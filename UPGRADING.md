# Upgrading Charming

This guide covers breaking changes on the road to 1.0, newest first. Each entry
shows before/after code for an app generated by an older version.

## Unreleased

### Components return `Components::Result` (custom components may keep the legacy forms)

Built-in components now return `Charming::Components::Result` from
`handle_key`/`handle_mouse`/`handle_paste`:

```ruby
# Before
def handle_key(event)
  case Charming.key_of(event)
  when :enter then return [:selected, selected_item]
  when :escape then return :cancelled
  end
  :handled
end

# After
def handle_key(event)
  case Charming.key_of(event)
  when :enter then return Result.selected(selected_item)
  when :escape then return Result.cancelled
  end
  Result.handled
end
```

Custom components do not have to change: the dispatch pipeline normalizes the
legacy forms with `Result.normalize`, with no deprecation. If your specs assert
on handler returns, `eq(Result.selected(item))` compares by kind and value.
`Result.changed(value)` exists as a reserved kind; no `on_change` DSL consumes
it yet.

### Session persistence is explicit per attribute

`save_session` used to skip state objects silently (they are not JSON-safe).
Declare what persists instead:

```ruby
# Before: the whole state object was dropped without a signal
class HomeState < Charming::ApplicationState
  attribute :count, :integer, default: 0
end
```

```ruby
# After: count survives restarts; everything else resets to its default
class HomeState < Charming::ApplicationState
  attribute :count, :integer, default: 0
  attribute :draft, :string, default: ""

  persist :count
end
```

During the transition, `save_session` warns once per dropped class or key
(category `:session_drop`), naming the `persist` declaration to add. Raw
`session[...]` values still pass through when JSON-safe and warn when dropped.
A stale session file (renamed class, changed attributes) logs a warning and
starts that state fresh instead of crashing boot.

### Component slots are declared with `slot`

Interactive components used to need four sites to agree: a private method, a
`focus_ring` entry, a layout pane name, and the `on_*` registration. Declare
the component once instead:

```ruby
# Before
focus_ring :query, :results

def show
  render :show, query: query, results: results
end

private

def query
  @query ||= Components::TextInput.new(placeholder: "Search…")
end

def results
  @results ||= Components::List.new(items: [])
end
```

```ruby
# After
slot :query   { Components::TextInput.new(placeholder: "Search…") }
slot :results { Components::List.new(items: []) }

on_submit :query, :run_search

def show
  results.items = Entry.recent_first.to_a   # data refresh; selection survives
  render :show, query: query, results: results
end
```

The `slot` factory runs against the controller and its result is memoized for
the screen's lifetime. A private reader named for the slot is defined, so
action/view code is unchanged. With no explicit `focus_ring`, Tab cycles the
declared slots in declaration order; an explicit `focus_ring` still wins and
may name component-less panes like `:sidebar`.

The method convention still resolves but warns once per controller and slot.
It is removed at 1.0. Two stays-methods exceptions: form builders
(`form(:name)`) and modals rebuilt per dispatch from the record under review.

New validation catches declaration gaps. A focusable layout pane (`pane :name,
focus: true`) that nothing declares raises `Charming::UnknownSlot` in
development and test — declare it with `slot`, add it to `focus_ring`, or
define a same-named method. `on_submit`/`on_select`/`on_cancel` registrations
for undeclared slots raise the same error at first dispatch. Production logs a
warning instead.

### Task blocks take data in via `with:`

`run_task` blocks now receive a `Charming::Tasks::Context`. Inputs travel in a
`with:` hash, deep-frozen at submit time; `ctx.report(...)` replaces the old
progress argument:

```ruby
# Before
run_task(:export) do |progress|
  entries.each { |entry| write(entry) }
  progress.report(1, of: 1)
end

# After
run_task(:export, with: {entries: entries}) do |ctx|
  ctx[:entries].each { |entry| write(entry) }
  ctx.report(1, of: 1)
end
```

Blocks that never took an argument are unchanged. Existing `|progress|`
blocks keep working — the context still responds to `report` — but move every
value the block closes over into `with:`.

The rule is now enforced in development and test: calling `render`,
`navigate`, `quit`, `session`, `focus`, or `component_for` from the task
thread raises `Charming::CrossThreadAccess`. The error lands in the task's
`TaskEvent` as `event.error`. Handle results in the `on_task` handler — that
runs on the loop thread and may touch state freely.

### Setting the response twice in one dispatch raises

`render`, `render_view`, `render_template`, `navigate`, and `quit` all assign
the dispatch's response. A second assignment in the same dispatch used to
overwrite the first silently. It now raises `Charming::DoubleRenderError`:

```ruby
def show
  render "Old frame"      # dead: the navigate below discarded it
  navigate :dashboard
end
```

The fix is to delete the dead first call:

```ruby
def show
  navigate :dashboard
end
```

The error message names the action, the response already set, and the one
attempted. A response set outside a dispatch (in `screen_entered`, say) is
discarded when the next dispatch starts — it never painted anyway, so move
that work into the action.

One framework behavior changed with this: a command-palette command that
calls `render` now keeps its own response. Before, the default render ran
after the command and overwrote it.

### The sidebar and command palette are opt-in shell modules

The kernel controller no longer includes sidebar navigation or the command
palette. If your app uses them (any app generated with the sidebar layout),
include the shell modules in your `ApplicationController`:

```ruby
class ApplicationController < Charming::Controller
  include Charming::Shell::Sidebar
  include Charming::Shell::Palette

  # focus_ring, command entries, and the rest work as before
end
```

Running `charming generate layout` adds the includes for you. The `command`
class DSL comes with `Charming::Shell::Palette`; `key`, `timer`, `animate`,
and `on_task*` stay in the kernel.

Apps that never used the sidebar or palette need no changes — shell-less
controllers handle keys, mouse, and tab traversal unchanged.

### Controllers are persistent per screen

One controller instance now lives for as long as its screen is active. The
Runtime constructs it at route entry and dispatches every event at it.
Instance variables are legal screen-lifetime state:

```ruby
def show
  render "Count: #{@count || 0}"
end

def increment
  @count = (@count || 0) + 1   # survives across key events
  show
end
```

Navigating away discards the instance; coming back builds a fresh one. Two
hooks bracket the lifetime — override them to start/stop per-screen resources:

```ruby
def screen_entered
  @player = Audio::Player.new
end

def screen_exited
  @player&.stop
end
```

The state rule of thumb:

- **Ivars** for screen-lifetime (components, drafts, counters).
- **`state(name, Klass)` objects** for app-lifetime (survives navigation).
- **`persist_session`** for restart-lifetime (JSON-safe values only).

Most old code keeps working: `state(...)` and `session` are unchanged, and
`component_state` still works but warns — replace it with memoized ivars:

Before:

```ruby
def query
  state_hash = component_state(:query, value: "", cursor: 0)
  TextInput.new(value: state_hash[:value], cursor: state_hash[:cursor])
end
```

After:

```ruby
def query
  @query ||= Components::TextInput.new
end
```

Data-bound components need both halves: memoize the component so its
interaction state (selection, scroll) survives, and refresh its data on
render. `List#items=` and `Table#rows=` exist for exactly this:

```ruby
def show
  entries.items = Entry.recent_first.to_a
  render :show, entries_list: entries
end

def entries
  @entries ||= Components::List.new(items: Entry.recent_first.to_a, ...)
end
```

Rebuilding the component per dispatch instead would discard the keypress that
moved the selection before any state write-back could see it.

Form state moved from `session[:forms]` to the controller instance. Clear a
submitted form with `reset_form(:entry)` instead of `session[:forms]&.delete(:entry)`.

In tests, construct one controller and dispatch events at it:

Before:

```ruby
response = press(SearchController, "enter", app: app)
```

After:

```ruby
ctrl = build_controller(SearchController, app: app)
response = press(ctrl, "enter")
```

`Controller.new(event:)` still works for one release but warns; pass the event
to the dispatch method instead: `ctrl.dispatch_key(key_event("e"))`.

### Component event handlers are declared explicitly

Component results (`[:submitted, value]`, `[:selected, value]`, `:cancelled`)
used to find a controller hook by naming convention. Declare the handler with
the `on_*` class DSL instead:

Before:

```ruby
class SearchController < ApplicationController
  def query_submitted(value)
    # ...
  end
end
```

After:

```ruby
class SearchController < ApplicationController
  on_submit :query, :run_search

  def run_search(value)
    # ...
  end
end
```

The declarations are `on_submit`, `on_select`, and `on_cancel`. Actions for
`on_submit`/`on_select` receive the value; `on_cancel` actions receive no
arguments.

The old convention still works but emits a one-time deprecation warning naming
the declaration to add. A component result with no handler at all — the old
silent-fallback case — raises `Charming::UnhandledComponentEvent` in
development and test (this catches typos in hook names), and logs a warning in
production before falling back to the default render.

### Routes are named screens, not URL paths

`config/routes.rb` registers each screen under a Symbol name. `root` is
unchanged and registers the reserved `:root` screen.

Before:

```ruby
MyApp::Application.routes do
  root "entries#show", title: "Entries"
  screen "/compose", to: "compose#show", title: "Compose"
  screen "/entries/:id", to: "reader#show", title: "Entry"
end
```

After:

```ruby
MyApp::Application.routes do
  root "entries#show", title: "Entries"
  screen :compose, "compose#show", title: "Compose"
  screen :entry, "reader#show", title: "Entry"
end
```

Dynamic segments (`:id`) are gone. Register one named screen per parametric
page and pass the values when you navigate.

### `navigate` replaces `navigate_to`, and takes a name plus params

Before:

```ruby
def open_entry(entry)
  navigate_to "/entries/#{entry.id}"
end
```

After:

```ruby
def open_entry(entry)
  navigate :entry, id: entry.id
end
```

Params arrive with their Ruby values intact — `params[:id]` is whatever you
passed (an Integer id, a record, anything). There is no URL decoding and no
string conversion.

`navigate :root` replaces `navigate_to "/"`.

Code that still passes a string path raises `ArgumentError` with a migration
hint. `Router#resolve(:typo)` raises `KeyError` listing the registered names.

### Sidebar filtering by route

The `Route` struct's `path` member is now `name` (a Symbol). If you filter
`sidebar_routes`, match on names:

Before:

```ruby
def sidebar_routes
  application.routes.all.reject { |route| route.path.include?(":") }
end
```

After:

```ruby
def sidebar_routes
  application.routes.all.reject { |route| %i[entry edit_entry].include?(route.name) }
end
```

## Removals planned for 1.0

These still work but warn; they will be removed at 1.0. This list is
cumulative across releases.

- The auto-discovered `<slot>_submitted` / `<slot>_selected` /
  `<slot>_cancelled` hook convention. Declare handlers explicitly with
  `on_submit :slot, :action` / `on_select` / `on_cancel`.
- Resolving focus slots through same-named private methods. Declare the
  component with `slot :name { ... }`. (Form-builder methods and per-dispatch
  modal builders are exempt — they stay methods.)
- `component_state`. Memoize components in controller ivars instead.
- `Controller.new(event:)`. Construct once; pass events to the dispatch
  methods.
